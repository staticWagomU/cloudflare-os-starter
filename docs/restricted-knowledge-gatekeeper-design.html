Design review draft

Restricted Knowledge Gatekeeper Design

Cloudflare OS の上流を改造せず、一部社員だけが検索・閲覧・追加できる社内ナレッジ基盤を custom Gatekeeper と Cloudflare の管理リソースで検証し、将来 gigooo-identity に接続できる形で実装するための設計案です。

結論

Cloudflare OS の Context Gatekeeper は改造しません。 既存 Context は全社員向け・個人向けの軽いナレッジに使い、一部社員向けの AI Search は packages/custom-gatekeeper を Restricted Knowledge Gatekeeper として置き換えて実装します。

これにより、Cloudflare OS の submodule 更新で追従すべき境界を Gatekeeper 標準インターフェースに限定します。 上流の Context UI、Context storage、Workshop 内部 DB には直接手を入れません。 今回の検証では gigooo-identity に接続せず、Cloudflare Access の email などを暫定 principal として使います。 本番想定では社員の正準ID、Role、Permission を ../../Gigooo-organization/gigooo-identity に寄せます。

今回の検証方針

検証版では gigooo-identity を使いません。 代わりに Cloudflare Access で認証済みの email、またはローカル検証用の固定 user key を access_email または local_account principal として扱います。 これは検索、追加、Collection ACL、UI の動作を確認するための暫定手段です。

検証版の email principal は業務データの正準外部キーではありません。 本番化するときは D1 の ACL を identity_user / role / permission に移行し、email は表示・入力補助に戻します。

背景

相談内容は、NotebookLM に入れていたエンジニア情報、会話録、トラブル状況、MTG 内容を、 社内限定の AI Search として継続運用したいというものです。NotebookLM 的な「ノートに全部詰める」方式では、 ソース数やサイズ、権限分離、情報流出対策、継続投入の運用が課題になります。

Cloudflare OS には既に Context & Skills UI があり、Collection 作成と文書追加ができます。 ただし現状の Context は private / public の境界が中心です。一部社員だけに Collection を公開するために Context の visibility や ACL を上流コードへ直書きすると、Cloudflare OS 更新に追従しにくくなります。

設計目標

目標

  • Cloudflare OS 上の UI で Restricted Knowledge Collection を作成できる。
  • Markdown、議事録、会話録、トラブルメモを追加・更新できる。
  • Collection 単位で閲覧者と編集者を principal で制御できる。
  • Agent は検索・閲覧・追加を Gatekeeper API 経由で行う。
  • 検索結果と回答に根拠文書を返し、権限のない文書は検索にも閲覧にも出さない。
  • Cloudflare OS の上流更新時に、独自差分が submodule 内へ残らない。

非目標

  • Cloudflare OS の Context Gatekeeper を fork して ACL を追加しない。
  • Workshop の内部 DB や共有モデルを直接触らない。
  • 初期版では Slack / Google Drive / Meet 連携の自動同期までは含めない。
  • LLM の回答だけを保存して原文を捨てる設計にはしない。
  • Access の入口制御だけで文書単位 ACL を代替しない。
  • 検証版のメールアドレス principal を、本番の正準外部キーとして扱わない。

上流追従の境界

領域 扱い 理由
cloudflare-os/ submodule 変更しない 更新衝突を避ける。Gatekeeper 標準インターフェースだけを依存点にする。
packages/custom-gatekeeper 主実装 この starter が想定する wrapper-owned Gatekeeper の置き場所。
scripts/deploy.ts binding 追加時のみ最小変更 D1 / R2 / Vectorize / AI binding を custom Gatekeeper に渡す必要がある。
deployment.jsonc 非 secret の設定だけ追加 Worker 名、resource ID、機能フラグは設定値。秘密情報は入れない。

現在の deploy script は Workshop に GATEKEEPER_COLLECTIONS service binding を張っています。 つまり custom Gatekeeper は Cloudflare OS の公式拡張点として Workshop に見えます。

アーキテクチャ

Cloudflare Access 社員認証、アプリ入口制御、Access assertion
Router Worker Cloudflare OS の唯一の公開入口
Workshop Agent / Gadget から Gatekeeper を呼び出す
Restricted Knowledge Gatekeeper UI、検索、閲覧、追加、ACL 判定
Auth source + D1/R2/Vectorize 検証 principal、将来の Identity、metadata、原文、embedding index

Access はアプリ入口の認証です。検証版では Access email または固定 user key を暫定 principal にします。 本番想定では gigooo-identity が Cloudflare Access の認証結果から正準 user、role、 展開済み permission を返します。文書単位の認可は Gatekeeper が principal と D1 の ACL を照合して行います。 R2 は原文と正規化済み本文、D1 は metadata と ACL、Vectorize は semantic search 用の chunk embedding を持ちます。

認可モード

モード 使うもの 用途 注意
検証モード access_email / local_account principal Collection 作成、文書追加、検索、ACL UI の動作確認。 email は暫定キー。社内本番データの正準キーにしない。
本番想定モード identity_user / role / permission gigooo-identity の user.id、roles、permissions による共有制御。 今回の検証では実装しないが、schema と API は移行可能な形にしておく。

本番想定の Identity 連携

この節は将来設計です。今回の検証実装では gigooo-identity に接続しません。 gigooo-identity を社員 ID と認可情報の正本として使います。 Identity API は Cloudflare Access の assertion と呼び出し元 Service Token を検証し、 user.id、email、roles、permissions を返します。 業務データの正準キーは user.id です。メールアドレスは表示・入力補助には使えますが、 Collection owner や ACL の永続キーにはしません。

項目 設計上の扱い
identity.user.id Collection owner、document created_by、user ACL の正準キー。
identity.user.email UI 表示、入力補助、監査ログ表示。永続 ACL の主キーにはしない。
identity.roles 部署・チーム相当の共有単位として使う。例: knowledge:engineering。
identity.permissions アプリ操作の coarse gate に使う。例: knowledge:collection.manage。

実装時は @gigooo/identity-sdk の fetchIdentity() / createIdentityClient() を使う想定です。 SDK は同一 request の Identity API 呼び出しを cache し、必要に応じて短時間の snapshot store を使えます。 ただし 401/403 や期限切れ JWT を古い snapshot で上書きしない契約なので、権限剥奪に対して fail-open しません。

検証版では auto-provision を使わず、connectAccount() がnonce付き接続URLを返します。 Router経由のHTTP requestに付いたAccess JWTをGatekeeperが署名、issuer、audienceまで検証し、 検証済みemailでaccountを完成させます。raw headerのemailや固定email設定はprincipalに使いません。 本番のIdentity移行時は、このHTTP接続点でAccess assertionをIdentity APIへ渡し、 email principalを正準user idへ移行します。

ACL の最終判定は D1 で行います。Vectorize metadata filter は絞り込みの高速化に使えますが、 権限判定や鮮度スコアの唯一の根拠にはしません。

タグと鮮度

タグは Collection と Document の両方に付与できます。Collection tag は分類や既定の絞り込みに使い、 Document tag は検索 filter、検索結果表示、再ランキングに使います。タグは自由入力にすると表記ゆれが増えるため、 UI では既存タグの補完と新規タグ作成を分けます。

日付は created_at だけではなく source_date を持ちます。 source_date は「この情報が扱っている時点」です。会議録なら会議日、障害メモなら発生日または最終更新日、 社員情報なら確認日を入れます。取り込みが遅れても、情報の古さを正しく扱うためです。

項目 使い方
tags 検索 filter、検索結果の説明、Collection 管理画面での絞り込みに使う。
source_date 鮮度スコアの基準日。情報の内容が古いほど検索順位を下げる。
freshness_policy evergreen は減衰を弱くし、time_sensitive は減衰を強くする。 
finalScore =
  vectorScore
  * aclAllowed
  * freshnessWeight(sourceDate, freshnessPolicy)
  * tagBoost(queryTags, documentTags)

鮮度とタグは Vectorize の一次 filter にも使えますが、最終順位は Gatekeeper 側で D1 metadata を読んで再計算します。 これにより、古い情報を完全に消さず、必要なら「古いが関連する情報」として下位に残せます。

Agent 向け API

API は capability-based にします。Agent が任意の D1/R2 キーを直接指定して広く読める形にはしません。 初期 API は検索・閲覧・追加に絞ります。 

export interface KnowledgeCollectionSummary {
  id: string;
  title: string;
  description: string;
  role: "reader" | "editor" | "owner";
  tags: string[];
}

export interface KnowledgeSearchResult {
  documentId: string;
  collectionId: string;
  title: string;
  excerpt: string;
  sourceType: string;
  sourceDate?: string;
  tags: string[];
  freshness?: "fresh" | "aging" | "stale" | "evergreen";
  score?: number;
}

export interface KnowledgeDocument {
  id: string;
  collectionId: string;
  title: string;
  content: string;
  sourceType: string;
  sourceDate?: string;
  tags: string[];
}

export type KnowledgePrincipal =
  | { type: "access_email"; id: string }
  | { type: "local_account"; id: string }
  | { type: "identity_user"; id: string }
  | { type: "role"; id: string }
  | { type: "permission"; id: string };

export interface KnowledgeCollectionInput {
  title: string;
  description: string;
  readers: KnowledgePrincipal[];
  editors?: KnowledgePrincipal[];
  tags?: string[];
}

export interface KnowledgeDocumentInput {
  collectionId: string;
  title: string;
  body: string;
  sourceType?: "meeting" | "incident" | "note" | "transcript" | "employee" | "other";
  sourceDate?: string;
  freshnessPolicy?: "default" | "evergreen" | "time_sensitive";
  tags?: string[];
}

export interface RestrictedKnowledgeSession {
  listCollections(): Promise<KnowledgeCollectionSummary[]>;
  createCollection(input: KnowledgeCollectionInput): Promise<KnowledgeCollectionSummary>;
  search(query: string, options?: {
    collectionId?: string;
    tags?: string[];
    from?: string;
    to?: string;
    freshness?: "prefer_recent" | "include_stale";
    limit?: number;
  }): Promise<KnowledgeSearchResult[]>;
  readDocument(documentId: string): Promise<KnowledgeDocument | null>;
  addDocument(input: KnowledgeDocumentInput): Promise<KnowledgeDocument>;
}

createCollection() と addDocument() は外部世界に見える永続的な副作用です。 Gatekeeper の approval queue では read は observation、write は action として扱い、 実装時に submit / apply / reject の設計を分けます。

Cloudflare OS 上の管理 UI

custom Gatekeeper の AccountDescription に providesUi を追加し、 startAppUi() で管理画面を提供します。UI は Cloudflare OS の Connector 画面から開き、 Restricted Knowledge 用の Collection 管理を行います。

画面 機能
Collection list 自分が owner/editor/reader の Collection を一覧表示。権限と最終更新を表示。
Create collection 名前、説明、reader/editor の principal を設定。検証版では email、本番想定では Identity User / Role / Permission。
Document editor Markdown 追加・編集、source type、source date、タグ、鮮度ポリシー、要約説明の入力。
Access settings owner が reader/editor を更新。監査ログを表示。
Search preview その Collection 内で検索結果がどう見えるか確認。タグ filter と鮮度補正後の順位も表示。
Tag management タグの作成、説明編集、統合、未使用タグの確認。

権限設計

権限 できること
reader 検索、文書閲覧。追加・編集不可。
editor reader の操作に加えて、文書追加・編集・削除。
owner editor の操作に加えて、Collection 設定と ACL の変更。
admin 運用上の break-glass。通常の検索結果には自動混入させない。

Access policy は「このアプリに入れる社員」を決めるだけです。 「この文書を読める社員」は Gatekeeper が現在の principal と D1 の ACL で毎回判定します。 検証版では access_email または local_account、 本番想定では gigooo-identity の user/role/permission を使います。 この二重化を崩すと、一部社員向けの要件を満たせません。

Observer policy

Gadget が共有されたとき、過去に Gatekeeper が読んだ情報を collaborator が見られる可能性があります。 Restricted Knowledge は低リスク情報ではないため、現在の custom Gatekeeper example のような no-op verifier は使いません。

方針は data-set tracking です。Gatekeeper は観測済み Collection ID を Durable Object storage に記録し、 addObserver() 時に observer の principal が全 Collection を読めるか確認します。 新しい Collection を初めて観測する read では、既存 observer に対して再確認し、権限がない observer を excludeObservers に入れます。

検索・追加フロー

検索

  1. 検証版では署名検証済みAccess email、またはローカルaccount idから access_email / local_account principalを作る。
  2. 本番想定では Access assertion から gigooo-identity を呼び、user.id、roles、permissions を解決する。
  3. principal に一致する reader/editor/owner の Collection を D1 で引く。
  4. query を Workers AI embedding model で embedding 化する。
  5. Vectorize に問い合わせる。必要なら collection metadata、tag、date で一次 filter する。
  6. hit の document / collection を D1 で再確認し、読めないものを落とす。
  7. D1 の source date、freshness policy、tags を使って再ランキングする。
  8. R2 から chunk text を読み、observation を記録して検索結果を返す。

追加

  1. 呼び出し元 principal を解決し、Collection に対する editor/owner 権限を D1 で確認する。
  2. approval queue に action を登録する。
  3. apply 時に D1 document record、tag relation、R2 normalized text、chunk、Vectorize vector を作る。
  4. 途中失敗時は retry 可能な indexing status を D1 に残す。

必要な Cloudflare binding

binding 用途 候補名
D1 Collection / document / ACL / audit / indexing status KNOWLEDGE_DB
R2 原文、正規化 Markdown、chunk text KNOWLEDGE_OBJECTS
Vectorize semantic search index KNOWLEDGE_INDEX
Workers AI embedding 生成 WORKERS_AI または custom worker 側の AI binding
Vars 検証版の認可モードと、将来の Identity 接続設定 AUTH_MODE=local_account、または AUTH_MODE=access_email と BASE_URL, CF_ACCESS_ISS, CF_ACCESS_AUD。本番想定では IDENTITY_API_URL, IDENTITY_APP_ID を追加。
Secrets 本番想定の Identity API 呼び出し用 Service Token 今回の検証では不要。本番想定では IDENTITY_SERVICE_CLIENT_ID, IDENTITY_SERVICE_CLIENT_SECRET。
KV optional 本番想定の Identity SDK 短時間 snapshot store。5xx / network failure 時だけ使う。 今回の検証では不要。本番想定では IDENTITY_SNAPSHOTS。

Cloudflare docs 上、D1 は Workers から binding 経由で使う serverless SQL database、R2 は大容量の unstructured data 向け object storage、 Vectorize は Workers から embedding を保存・検索する vector database と説明されています。 Identity 用 Service Token secret は今回の検証では作らず、本番想定でも deployment.jsonc や tracked file には置きません。

段階的実装計画

Phase 内容 完了条件
0. API review この設計、agent-facing API、検証モードの principal 解決方式をレビューする。 API 名、権限、UI 範囲、storage 方針、検証モードの境界が承認される。
1. Verification read-only core access_email / local_account principal と D1/R2 の Collection、document、tag、source date を使い、list/search/read を実装する。 検証 principal に基づく権限つき検索、タグ filter、鮮度再ランキング、observation がテストで通る。
2. UI creation Cloudflare OS 上の Gatekeeper UI で Collection 作成と document 追加を実装する。 UI 操作で D1/R2 に保存され、read API で読める。
3. Write actions Agent からの create/add/update を approval queue action として実装する。 submit/apply/reject/revert の挙動が明確にテストされる。
4. Vectorize chunking、embedding、indexing retry、metadata filter、D1 metadata による再ランキングを実装する。 検索品質、タグ filter、鮮度補正、ACL 後段判定が評価ケースで確認される。
5. Identity migration design gigooo-identity 連携、principal migration、Identity Service Token、Access assertion の伝播方式を確定する。 検証版の access_email / local_account ACL を Identity principal へ移行できる計画がレビューされる。
6. Observer hardening data-set tracking observer policy を実装する。 共有 Gadget で権限外 Collection が見えないことを検証する。

テスト方針

  • unit: principal matching、ACL 判定、role order、tag normalization、freshness scoring、document path validation、chunking。
  • auth: Access JWTの署名、issuer、audience、email claim、接続nonceの期限と再利用拒否。
  • worker tests: Gatekeeper session の list/search/read/add と approval queue の呼び出し。
  • migration tests: D1 schema migration と seed data。
  • integration: 検証版では access_email / local_account の owner/editor/reader/denied user の操作差分。
  • future integration: gigooo-identity の user.id / roles / permissions を使った owner/editor/reader/denied user の操作差分。
  • search quality: 同じ関連度なら新しい情報が上に来ること、evergreen は不必要に下がらないこと。
  • security: 検索 hit の Vectorize metadata を偽っても D1 ACL で落ちること。
  • upgrade: Cloudflare OS submodule 更新後も custom package と deploy script の境界だけで差分確認できること。

リスクと保留事項

項目 判断
user identity を custom Gatekeeper がどう受け取るか 検証版はnonce付きHTTP接続点でAccess JWTを検証し、access_email accountを作る。local_accountはローカル検証専用。本番のIdentity移行では同じ接続点からIdentity APIを呼び、正準user idへの移行と既存ACLの変換手順を別途レビューする。
Role / Permission を共有単位としてどこまで使うか gigooo-identity の can() は exact-match 前提で、wildcard / deny / inheritance を持たない。Collection 共有に使う role / permission 名を初期実装前に固定する。
個人情報・機微情報 source type と classification を D1 に追加し、検索対象から除外できるようにする余地を残す。
外部 provider 利用 初期版は Workers AI embedding を優先。OpenAI/Anthropic 等を使う場合は data handling を別レビューする。
大規模取り込み 初期 UI 追加後に、Google Drive / Slack / Meet transcript 同期を別 Gatekeeper または batch として設計する。
